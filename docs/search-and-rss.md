# Search and RSS

## Decision and measured experiment

Phase 4 uses Pagefind 1.5.2 after the Astro build. It indexes rendered published articles, keeping MDX imports and component source out of results. No search service, React app, or visitor tracking is added. The search client loads the engine only after a nonempty query is submitted.

A five-article experiment on 2026-10-20 compared metadata-only JSON with rendered-body search. Metadata JSON was 1,177 bytes raw / 629 bytes gzip; metadata plus normalized prose was 8,732 bytes raw / 3,537 bytes gzip. Pagefind indexed five pages and 476 unique words in that experimental corpus. Eight test queries covered beam steering, windowing, Rayleigh, VSWR, feature engineering, Hann, impedance matching, and an absent token. Both approaches found the five title/description concepts; metadata missed the body-only Hann and impedance-matching queries. Pagefind found both, and correctly returned no results for the absent token. VSWR also matched an additional article that mentions it; these are lexical results, not expert recommendations.

Across those eight queries the browser fetched 169,573 response-body bytes of Pagefind runtime, worker, language engine, metadata, index, and result fragments. This is decoded response-body size, not HTTP transfer size or a cold single-query measurement. Pagefind has higher fixed overhead than the tiny JSON alternatives at the current archive size. We accept that cost for rendered-content indexing, language stemming, ranked excerpts, and a chunked index as writing grows. A custom full-text JSON engine would need its own ranking/tokenization and MDX-text extraction; adding Fuse/MiniSearch would still need content extraction and a full client index. Revisit if measured search performance becomes a problem. No claim of semantic or mathematical-symbol search is made.

Sources: [Pagefind indexing](https://pagefind.app/docs/indexing/), [search API and lazy result data](https://pagefind.app/docs/api/), [Astro static endpoints](https://docs.astro.build/en/guides/endpoints/).

## Boundaries and behavior

`getAllPosts()` determines publication eligibility before article routes exist. `data-pagefind-body` on the article layout restricts indexing to those routes. `pagefind.yml` excludes KaTeX's duplicate formula markup, interactive islands, contents, article-tool sections, and explicitly ignored elements. Surrounding explanations and rendered code blocks are searchable; formulas are read in their original article context. Titles and readable topic labels are returned as metadata. New template or component changes should retain these boundaries.

`/search` is a dedicated native navigation destination. A labeled GET form uses `q`, so searches can be bookmarked. JavaScript enhances submission with loading, results, empty, and retry states; results are ordinary links. Ten results load at a time. Keyboard focus starts on the query for a fresh search-page navigation, stays on the control when submitting, and moves to the first newly loaded result after Show more. Escape clears the query. No automatic per-keystroke requests or focus-trapping dialog. With JavaScript disabled, topic links and the writing index remain usable and a message explains the limitation.

`npm run build` must finish both Astro and Pagefind. `astro build` alone is insufficient for deployable search. The GitHub workflow already invokes `npm run build`; its separate output-check gate remains deferred. Search indexes are generated into `dist/pagefind`, never committed. In dev mode the index is unavailable: use `npm run build && npm run preview` to exercise production search. A missing engine or network failure displays a retry/browse message instead of an empty success state. Failed result downloads reset Pagefind before retry because its fragment cache retains rejected downloads.

## RSS and authoring

`/rss.xml` is summary-only RSS 2.0, generated by a static Astro endpoint from `getAllPosts()`. Each item uses its title, description, publication date, readable topic, absolute article URL, and stable permalink GUID. XML text is escaped. The feed deliberately omits full MDX/KaTeX/interactive HTML. Every regular page advertises it in the head and links it in the footer. Subscribe using the absolute feed URL `https://frah90.github.io/rss.xml`.

Drafts have no article route and therefore no Pagefind document. They are also absent from listings, category routes, related cards, RSS, and the sitemap. Always set `draft: true` explicitly while writing. Before publishing, inspect search terms and excerpt quality as well as the article itself. Search and feed contain the current trial articles because their existing publication status is unchanged; inclusion does not certify their scientific claims.

## Verification

After `npm run build`, run `npm run check:build`. It checks article/search page counts, feed membership and dates, discovery links, and the existing public-link/fragment/sitemap boundaries. Browser checks must still cover known queries and no results, query URLs, pagination, loading and failure recovery, mobile/desktop layouts, both themes, keyboard focus, and JavaScript-disabled browsing. XML parsing and a temporary draft fixture check the publication boundary independently of index counts. This is a summary feed; full-article feeds would need a separate rendering/security decision.
